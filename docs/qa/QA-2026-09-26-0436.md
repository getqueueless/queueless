## P0 — open redirect on `/login?next=` (already messaged, recording here)

Steps: `https://lpu.lol/login?next=/%5Cevil.com`, sign in with any account.

Actual: browser navigates to `https://evil.com/` after successful auth. Confirmed via `location.href`, `location.hostname` ("evil.com"), and `document.title` ("Evil.Com — We get it...Daily.") — a real, live navigation, not just a bad link. The backslash in `/\evil.com` is interpreted as a protocol-relative `//evil.com` by the browser; the `next` param is never validated to stay same-origin before the post-login redirect fires.

Impact: textbook phishing primer — send a real lpu.lol login link with this `next`, victim authenticates for real, then lands on an attacker page. Owner: web-admin/web-patient (post-login redirect logic). **Fix pending per the orchestrator ("an open-redirect fix is coming").**

## P1 — 91-prefixed mobile number truncated client-side (already messaged, recording here)

`supabase/migrations/0060_phone_normalization.sql`'s `private.normalize_in_phone` explicitly accepts bare-10-digit, `91`-prefixed, and `+91`-prefixed phone input and normalizes all three to `+91XXXXXXXXXX`. But `/my/profile`'s mobile `<input>` has `maxLength="10"` in the DOM — confirmed via `element.maxLength`. Typing `919876543210` (12 chars, the exact form a user who includes their country code would type) gets silently truncated to `9198765432` before submit, which then correctly fails `^[6-9]\d{9}$` and shows the generic "Enter a 10-digit Indian mobile number" — even though the backend was specifically built to accept the untruncated input. The server-side fix in `0060` is unreachable through the UI. Owner: web-patient (raise/remove the client `maxLength`, or normalize before submit).

## P1 — counter open/closed state doesn't push live to an already-open `/counter` tab

Steps: `counter1` on `/counter` (desk `OPD-2`, `Closed`, Call Next disabled). Admin opens `OPD-2` (`Closed` → `Open`) via `/admin/counters`, confirmed saved (admin's own list shows `Open`). `counter1`'s tab, left untouched, still showed `Closed` / Call Next disabled after 13+ seconds. A manual reload immediately showed `Open` / Call Next enabled — so the data path is correct, only the live push to an already-open counter console is missing.

Same class of issue as the original token-status live-update bug (fixed earlier this pass via DB broadcast), but on a different topic — counter state changes aren't wired into the same broadcast the token-status page uses. Real-world impact: staff sitting at a desk when admin opens it won't see Call Next enable until they manually refresh. Owner: api (broadcast wiring for counter state) / web-admin (consumer).
