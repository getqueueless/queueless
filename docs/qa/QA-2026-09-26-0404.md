## 9b. NEW: TV board says "No counters open yet" despite an open counter

Route: `/display/<service-id>`, reproduced on Pediatrics.

Steps: with counter `PED-1` open and serving (confirmed via `board_counters`: `{"counter_name":"PED-1","state":"open","token_code":"PED-008","token_status":"done"}`), load `/display/<pediatrics-service-id>`.

Expected: shows PED-1 as an open counter (idle between patients is still "open").

Actual: "No counters open yet." Confirmed this isn't a data problem — direct query of the same data the page fetches (`counter_services` → `board_counters`) returns PED-1 correctly as `state: "open"`. So the client-side logic that decides what counts as "open" is excluding a counter whose last-served token is in `done` status. Screenshot: [35-tvboard-no-counters-open-bug.png](screenshots/35-tvboard-no-counters-open-bug.png)

This might be the same code path the earlier "flashing empty board on cold load" fix (`f62b416`) touched — worth checking there first, since it sounds like related logic for deciding when to show "no counters."

## 18. PostgREST access-control scan (new, non-destructive)

Method: for all 21 tables in `public`, ran GET (small limit), PATCH and DELETE (filtered on a UUID/id that matches nothing, e.g. `id=eq.00000000-0000-0000-0000-000000000000` — guaranteed to touch zero rows even if permitted), and POST with an empty body (fails safely on `NOT NULL`/FK constraints if permitted) — each with (a) the public anon key and (b) a real `QA_PATIENT2` session JWT obtained by signing in normally. Full raw results are in the branch history if anyone wants them; this section has the findings that matter.

### Already fixed, verified holding
**`profiles` role self-escalation** (`0045_profiles_rls.sql`, landed this pass): confirmed a patient JWT cannot PATCH the `role` column at all — `403 permission denied for table profiles`, even targeting their own row. The column-level grant correctly excludes `role`/`org_id`. This was the hole the DB engineer's migration note described (any patient could previously `PATCH /profiles?id=eq.<self> {"role":"admin"}` and grant themselves admin). **Confirmed closed.**

### Correctly locked down (no issue)
`cash_receipts`, `payments`, `walkin_patients` — anon gets 401, patient gets 403 on GET. Good.

### NEW — four tables have no RLS at all, and grants are wide open

| Table | anon | authenticated (patient) | Real-world impact |
|---|---|---|---|
| **`tokens`** | GET ✅, PATCH ✅ (204) | GET ✅, PATCH ✅ (204) | Anyone with just the public anon key — **no login required** — can read and modify **any patient's queue token**: reassign it, change its status/code/priority, by its `id` (which is printed on every slip, TV board and `/t/<id>` URL). |
| **`appointments`** | blocked (401, correctly) | GET ✅ (saw another patient's real booking), PATCH ✅ (204) | Any signed-in patient can read and modify **any other patient's appointment**, not just their own. |
| **`audit_log`** | blocked (401, correctly) | GET ✅ (5,148 rows, the *entire org's* audit trail), PATCH ✅ (204) | Any patient can read the full internal change history (including role/profile change diffs) and has UPDATE grant on what should be an append-only log. |
| **`counter_services`** | PATCH ✅ (204) | PATCH ✅ (204), DELETE ✅ (204) | This is the counter↔service assignment table that drives which desk serves which queue — writable by anon. |

None of these four have an `enable row level security` statement anywhere in `supabase/migrations/`. For `tokens` and `counter_services`, **anon** (the public key baked into every browser) can write, with zero authentication — that's the most severe of the four, since there's no login step to even slow it down. `appointments` and `audit_log` require being signed in as *any* patient, but that's a QA_PATIENT-tier account, trivially self-serve via `/login`.

Caveat on the PATCH/DELETE numbers: because the filter is deliberately built to match zero rows (per your non-destructive instruction), a `204` proves the **role has the table-level grant** — it doesn't by itself prove RLS wouldn't otherwise block a real row. But for these four tables there is no RLS at all, so the grant *is* the only gate, and the GET results already prove real cross-user rows are reachable on `appointments`/`tokens`. I did not attempt a write against a real row — that would cross into destructive testing.

### Worth a look, less urgent
`ops_summaries` (patient GET returns empty — fine, likely just no data yet, but PATCH grant exists), `notifications` (patient has SELECT on their own kind + PATCH grant on `read_at`, consistent with intended design per `0032_notifications_client_writes.sql`), `board_counters`/`board_services`/`counters`/`doctors`/`doctor_schedules`/`doctor_status`/`doctor_breaks`/`doctor_leaves`/`services`/`organizations` all grant PATCH to anon and/or authenticated even though RLS is technically enabled on them — worth a policy audit since these are operational/admin config tables that patients and the public shouldn't be able to write to at all, defense-in-depth-wise, even if no live hole was proven here.

**Recommended next step for db/api:** treat `tokens`, `appointments`, `audit_log`, `counter_services` the same way `profiles` was just treated in `0045` — enable RLS and add scoped policies (own-row for patients on `tokens`/`appointments`, staff-of-org read for `audit_log`, staff-only write for `counter_services`). This is the same class of bug as the one already fixed this pass, just on four more tables.
