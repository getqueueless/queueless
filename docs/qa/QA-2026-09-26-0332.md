### 8. NEW — P0: patient profile mobile-number validation rejects valid numbers

Route: `/my/profile` (the "One quick step" profile gate every non-profile-complete account must clear before taking a token or booking).

Steps:
1. Sign in as a patient/account with no saved profile (e.g. `QA_PATIENT2`).
2. Fill all fields correctly, including a mobile number in the field's own displayed format (`98765 43210` — 5 digits, space, 5 digits, starting 6–9).
3. Submit.

Expected: profile saves.

Actual: **inconsistent** — some correctly-formatted 10-digit numbers are accepted, others are rejected with "Enter a 10-digit Indian mobile number" even though they match the exact shape of the field's own placeholder. Confirmed this is server-side, not a client rendering glitch: inspected the raw `POST /my/profile` request/response — the server received `_1_phone=91112 22334` and replied `{"error":"Fix the highlighted fields and try again.","fieldErrors":{"phone":"Enter a 10-digit Indian mobile number"}}`. The same account, same session, immediately retried with `78945 61230` and it was accepted. `98765 43210` was also accepted in an earlier attempt.

This blocks the entire profile gate — and therefore token-taking and booking — for any patient unlucky enough to enter a number the (apparently non-deterministic, or mis-mapped) validator rejects, with a generic error that gives no indication of the real cause. One plausible root cause: several QA/dev sessions are likely hitting this same production database concurrently (this repo has sibling worktrees for api/db/mobile/web/webadmin/pay), and a duplicate-phone unique-constraint violation is being caught and reported through the same generic "Enter a 10-digit Indian mobile number" message instead of "already registered" — worth checking server logs for the literal rejected values against existing rows before assuming it's a regex bug.

Owner: **api** (validation/constraint-error mapping) — flagging web-patient too in case it's a client-side race re-submitting a stale value.

### 9. NEW — P2: profile form wipes all fields on any validation error

Same `/my/profile` form: on any validation failure, every field the user already typed (name, DOB, city) is cleared back to empty, not just the field(s) that failed. Forces a full re-type on every failed attempt, which made bug #8 above much more painful to isolate. Owner: web-patient.
