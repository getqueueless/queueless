# Queueless apps/api Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task (single-engineer inline execution; tasks are grouped at feature-commit granularity, not micro-steps, because the implementer wrote this plan with full context and executes immediately after). Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build `apps/api`, a Python 3.12 FastAPI service that sits beside self-hosted Supabase and provides JWT-derived RBAC, Expo push notifications on token-state events, an idempotent multi-replica-safe no-show scheduler, a wait-time ML predictor with a responsible-AI fallback, and hackathon-grade security/ops hardening.

**Architecture:** Single FastAPI app (`app/main.py`) with an asyncpg connection pool for queries, one dedicated non-pooled asyncpg connection for `LISTEN token_events`, an always-on polling fallback for the same event (dedup-table-driven so both paths are safe to run concurrently), a fixed-interval asyncio scheduler task guarded by `pg_try_advisory_xact_lock`, and a joblib-persisted `HistGradientBoostingRegressor` loaded once at startup into `app.state`.

**Tech Stack:** FastAPI, asyncpg, PyJWT, pydantic-settings, slowapi, structlog, prometheus-fastapi-instrumentator, exponent-server-sdk, scikit-learn, pandas, joblib, pytest, uv.

## Global Constraints

- Python 3.12, managed with `uv`. `uv sync --frozen` must work; commit `uv.lock`.
- Only touch `apps/api/**`, `docs/api/**`, and the Backend/AI-ML/Security sections of `docs/JUDGE_NOTES.md`. Never touch `supabase/`, `apps/web`, `apps/mobile`, or root monorepo files.
- Commit after every small working step, conventional-commit subjects (`feat:`, `fix:`, `chore:`, `docs:`, `test:`), no AI attribution, trailers exactly as `apps/queueless-api/CLAUDE.md` specifies. `git pull --rebase origin main && git push origin HEAD:main` after every commit.
- Never fabricate a working feature. Where the DB team's schema/trigger isn't landed yet, build the documented fallback and say so in `docs/JUDGE_NOTES.md` and the final report — never silently paper over it.
- Every pydantic request model: `ConfigDict(strict=True, extra="forbid")`, constrained field types (no free-text used in branching/SQL).
- Role authorization always derives from verified JWT `sub` + a server-side table lookup — never from `role`/`user_metadata`/`app_metadata` claims or any client-supplied field.

## Cross-team dependency risk (called out up front)

As of this plan, `origin/main` has no `supabase/migrations` yet (repo only has the root `CLAUDE.md`/`.gitignore` init commit) — the DB team hasn't landed schema. This plan builds `apps/api` against the **documented** table/function names from the brief:

- `profiles(user_id uuid primary key, role text)` — authoritative app role.
- `tokens(id uuid pk, service text, status text, user_id uuid, called_at timestamptz, created_at timestamptz)` — state machine values assumed to include `waiting`, `called`, `served`, `no_show`, `cancelled`.
- `issue_token`, `call_next` — Postgres functions the DB team owns; `apps/api` never calls these directly, it only reads `tokens`/`profiles` and writes `push_tokens`/`token_notifications`, plus one `UPDATE tokens SET status='no_show'` in the scheduler.
- `pg_notify('token_events', ...)` trigger inside `issue_token`/`call_next` — **does not exist on origin/main yet**. Section 7 of this plan builds the LISTEN path so it activates the moment the trigger lands, but ships a polling fallback that is the real, working path today. This is reported honestly in `docs/JUDGE_NOTES.md` and the final report, not hidden.

If a real migration lands mid-build with different column/table names, adapt the SQL in `app/db.py`/`app/notifications.py`/`app/scheduler.py` and note the diff in the final report. Until then, tests spin up a throwaway Postgres via `podman run postgres:16-alpine` with a local fixture schema matching the names above — that fixture is test-only scaffolding, never written to `supabase/`.

**Interfaces locked now so later tasks match:**
- `app.auth.get_current_user(request) -> AuthedUser` where `AuthedUser` is a small dataclass/pydantic model `{user_id: UUID}` (identity only; no role).
- `app.auth.require_role(*roles: str) -> Callable` — a FastAPI dependency factory; internally calls `get_current_user`, then `app.auth.get_role(user_id) -> str` (TTL-cached profiles lookup), then 403s if not in `roles`.
- `app.scheduler.no_show_tick(pool: asyncpg.Pool, threshold_minutes: int) -> list[UUID]` — returns the ids that were transitioned; empty list means "no-op this tick" (either nothing eligible or lock not acquired).
- `app.ml_runtime.predict_with_fallback(model, meta, service, hour, weekday, queue_len_ahead, counters_open) -> dict` — returns `{"predicted_wait_minutes": float, "fallback": bool, "reason": str | None}`.
- `app.notifications.notify_if_new(pool, token_id, kind)` — inserts into `token_notifications(token_id, kind)` with `ON CONFLICT DO NOTHING RETURNING 1`; caller sends the push only if a row came back. Both the LISTEN handler and the poller call this same function, which is what makes running both concurrently safe.

## Task 6: Expo push sending + notification triggers (LISTEN + polling fallback)

**Files:** `app/notifications.py` (extend), `app/main.py` (lifespan wiring), `tests/test_notifications.py`.

- [ ] `notify_if_new(pool, token_id, kind) -> bool`: `INSERT INTO token_notifications(token_id, kind) VALUES ($1,$2) ON CONFLICT DO NOTHING RETURNING 1`; returns whether a row was inserted.
- [ ] `send_push(pool, user_id, message)`: reads all `push_tokens.token` for `user_id`, builds `PushMessage`s, `await asyncio.to_thread(PushClient().publish_multiple, messages)`, iterates tickets: `DeviceNotRegisteredError` -> delete that token row; `PushTicketError` -> log and continue.
- [ ] `poll_tick(pool)`: (a) for each `service`, rank `waiting` tokens by `created_at`; where rank = 3, `if await notify_if_new(pool, id, "third_in_line")`, send push "You're 3rd in line"; (b) `SELECT id, user_id FROM tokens WHERE status='called' AND id NOT IN (SELECT token_id FROM token_notifications WHERE kind='called')`, for each `if await notify_if_new(...,"called")` send push "You've been called".
- [ ] `listen_task(settings)`: opens a dedicated connection via `db.get_direct_connection`, `await conn.add_listener("token_events", handler)`, reconnect-with-backoff loop checking `conn.is_closed()`; handler parses the JSON payload and calls `notify_if_new` + `send_push` for the given kind — inert today since no trigger emits on `origin/main` yet, but ready the moment one lands.
- [ ] `poller_task(pool, interval)`: `while True: await poll_tick(pool); await asyncio.sleep(interval)` — this is the real, working path today; log once at startup: `"push notifications running in polling mode; LISTEN/NOTIFY trigger not yet present on origin/main"`.
- [ ] Wire both tasks in `main.py` lifespan; cancel+await both on shutdown.
- [ ] Tests (against the fixture DB): `notify_if_new` fires once and is a no-op on retry (dedup); `poll_tick` sends exactly one "third_in_line" push for the 3rd waiting row and one "called" push for a called row, using a fake `PushClient.publish_multiple` (monkeypatched — this is mocking a third-party HTTP call, not the feature under test).
- [ ] Commit: `feat: expo push notifications via polling fallback and LISTEN/NOTIFY hook`.
